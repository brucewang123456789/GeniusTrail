Author: Libo Wang.

This file records what was established by reading the record repository

directly, and the judgment that follows from it.

## 2. Where our argument would attach

`Zeta23/ThmD/Functional.lean` defines

    cFun lam v = lam·(∫v)² / (∫v² + lam²·∬|s−s'|·v(s)v(s'))    on [−1/2, 1/2].

At `lam = 1` this is `I₁²/(I₂+J)`, so `2 − 1/cFun 1 v = 2 − (I₂+J)/I₁² = H(v)` **identically**.
The record constant is `cStar 1`, the optimum of that functional; equivalently the record is
`sup_v H(v) = 0.6725007…`. This independently confirms the numerical `sup H` computed in
`NUMERICS.md`, and it identifies the record as *pure window optimisation with no block term*.

The hook is `Zeta23/ThmD/Final.lean`:

    theorem thmD_lam_abstract (Z : ZeroConfig) (H : PaperInputs Z) (P : Params)
        (hP : P.Valid) (hlam : P.lam < 1) : … (HD P.lam − ε)·N ≤ N₀* …

with `PaperInputs` (in `Zeta23/Hypotheses.lean`) bundling the explicit formula, Riemann–von
Mangoldt with local count, Chebyshev–Mertens, an MV-Hilbert inequality and the Gamma facts —
all proved unconditionally for `riemannZeta` in the library. The block layer already exists
inside (`blockInputsD`, `trG`, `trG2`, `Assembly`). Our improvement is exactly the step that
the paper's Theorem D discards: it keeps `Δ(M) ≥ h(E) + …` where Theorem D uses `Δ(M) ≥ 0`.

So the attachment point is identified and the analytic layer need not be redone. That part of
the task is bounded.

## 3. The verdict: the branch-and-bound proof cannot be formalized as it stands

The three local certificates were discharged by exhaustive interval branch-and-bound:

    s = 1/2    43,685,299 nodes (single run) / 16 shards
    s = 19/20  170,801,234 nodes
    s = 1      213,519,829 nodes
    total      ≈ 4.28 × 10^8 interval nodes

A Lean submission must be replayed by the Lean kernel **and** by an independent kernel
(`nanoda`) inside a credential-free sandbox. Kernel-checked reduction of a computation of this
size is not feasible — not by a reflective interval tactic, not by `native_decide` (which is
disallowed anyway, since it would add an axiom outside the permitted set). **Transcribing the
present proof into Lean is a dead end, and no amount of engineering effort changes that.**
This is stated here rather than discovered later by whoever attempts it.

## 4. The strategy that replaces it

What the kernel can check cheaply is a *short certificate*: a fixed, small algebraic witness
whose verification is a bounded rational computation. The three inequalities have the shape

    F_s(g) = Σ_r b_r g_r + s Σ_{i<j} a_ij W(y_j − y_i)  ≥  eps_s      on [0,∞)^8,

with `W(x) = (K(x)/K(0))²` and `K` a finite sinc sum — transcendental, so no polynomial
certificate applies directly. The route with the right shape is therefore two-stage:

1. **Polynomial relaxation.** On the reduced domain established in `NUMERICS.md` (every
   coordinate confined to `[0.9, 15.5]` and finitely many components after the separable
   span-1 reduction), replace `W` by a rigorous polynomial lower bound `W ≥ p` with an
   interval-controlled remainder — Chebyshev or Taylor with an explicit tail bound, exactly
   the technique already used for `sinc` in the verifier.
2. **Sum-of-squares certificate.** Seek a Positivstellensatz certificate for
   `Σ b_r g_r + s Σ a_ij p(y_j − y_i) − eps_s ≥ 0` on the box, i.e. an explicit SOS
   decomposition modulo the box constraints. Such a certificate is a fixed list of rational
   matrices; checking it in Lean is one rational matrix identity plus positive-semidefiniteness
   of small rational matrices — kernel-checkable in seconds.

Whether a certificate of manageable degree exists at these margins is an open question and is
the correct next research target. It is a different problem from the one solved here, and it
should not be conflated with it.

## 5. Honest status

* The mathematics of the finite-dimensional layer is closed and independently reproducible
  outside Lean (`CERTIFICATES.md`, `AUDIT.md`, `verify_exact.py`, `arb_window.py`).
* The analytic interface is public, unconditional and already formalized upstream.
* A Lean submission to the ledger is **not** achievable by porting this proof. It requires the
  short-certificate programme of §4, which has not been started.
* `Solution.skeleton.lean` in this directory fixes the three required statements and records,
  at each `sorry`, precisely which mathematical object must be supplied. It is a specification,
  **not** a proof, and is deliberately not submitted: an upload that fails consumes one of the
  three daily slots for the account.
